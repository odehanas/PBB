2. System overview

GovBudget is a web-based Programme and Performance-Based Budgeting (PBB) system used by the Department of Finance and government entities to prepare, submit, review and consolidate annual budgets, capture actuals, allocate shared cost to programmes and activities, track KPIs, and publish management-review and Power BI reporting.

Architecturally it is deliberately simple: one server-rendered ASP.NET Core MVC application and one Microsoft SQL Server database. There is no desktop client, no message broker, no cache server, no background worker service, no scheduled job and no file share. Uploaded supporting documents are stored inside the database, so the application server holds no business data.

5. Deployment topology

Figure 2 — Proposed EGA sandbox deployment topology, including the release path and optional outbound access.
One decision that determines whether the environment works on day one The application enforces HTTPS redirection, HSTS and Secure cookies. If TLS terminates at an EGA proxy and the internal hop to the application is plain HTTP, users will experience a redirect loop and rejected sign-in cookies. Either keep HTTPS end-to-end to the application, or confirm that X-Forwarded-Proto is sent and provide the proxy addresses — we then enable forwarded-headers handling in the application. Please confirm which topology the sandbox will use.

5.1 Current production environment (for reference)

GovBudget runs today on a commercial Windows/IIS shared-hosting service with SQL Server, published over Web Deploy. The application and database structure in that environment are identical to what is proposed above; only the hosting provider differs. Migration to EGA infrastructure requires no code change other than the configuration items in Section 9.

7.1 Privilege model — EGA decision required

The application applies small, idempotent schema upgrades at start-up (adding a missing column, creating a missing table, seeding the permission matrix). Two supported models:

  • Option A — simpler. The application login holds db_owner on this database only. Each release self-heals the schema on first start.
  • Option B — least privilege. We deliver a versioned DDL script per release for an EGA DBA to run in the change window. The application login then needs only db_datareader, db_datawriter and EXECUTE; the start-up checks detect the work is already done and take no action.

Option B requires no code change — only an agreed release process. Please confirm which model EGA requires.

Port 80 is required only if EGA wants an edge-level HTTP to HTTPS redirect; the application performs the redirect itself and issues HSTS.

8.1 Hostname and certificate

One DNS name and a matching TLS certificate (TLS 1.2 minimum, 1.3 preferred). The hostname must be provided to us before go-live: the application validates the Host header against an allow-list and will return HTTP 400 for an unlisted name. This is a one-line configuration value, not a code change.

8.2 Outbound access — EGA decision

Both outbound features are switchable off by configuration and nothing else depends on them. For EGA's data-protection review: when the assistant is enabled, the user's question and the query results returned by the application's internal tools are transmitted to the AI provider. The database is never exposed directly, and results are already restricted to the signed-in user's entity and cost-centre scope. Our recommendation is that both features remain disabled in the sandbox unless EGA explicitly approves them.

11. Acceptance checklist

Proposed joint verification once the sandbox is available. Each step either passes or identifies a specific fault.

  1. The sign-in page loads over HTTPS at the agreed hostname — confirms DNS, certificate, host allow-list and proxy topology.
  2. Administrator sign-in succeeds — confirms database connectivity and credential handling.
  3. No errors in the start-up log; role and permission tables populated.
  4. Create, submit and approve a budget line — confirms the write path and the permission matrix.
  5. Import an Excel actuals file — confirms upload limits and in-database document storage.
  6. Export a management-review report to Excel — confirms report generation.
  7. Recycle the application pool and reload: the user remains signed in — confirms the key ring is persisted and writable.
  8. Assistant panel either answers or reports that it is disabled, with no error — confirms the outbound configuration is as agreed.
