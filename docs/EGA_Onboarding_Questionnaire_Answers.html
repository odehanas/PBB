1. Development and Provenance

1.1 How was this application developed?
In-house, with the assistance of generative AI coding tools.
Description: The application was developed internally by the Department of Finance. Design, data model, business rules and review were driven by departmental staff, with an AI coding assistant used to accelerate implementation. No external vendor or contract was involved.
1.2 If generative AI coding tools were used, to what extent?
Substantial: significant components were generated, then reviewed and modified by the developer.
1.3 Which development tools or AI coding assistants were used?
Microsoft Visual Studio (IDE) together with Windsurf as the AI pair-programming assistant.
1.4 Do the developers hold professional software engineering experience or qualifications?
Partly — a mixed technical/business background rather than a formally-qualified software engineer; the developer's primary role is business/functional (finance), with development undertaken with AI assistance.
1.5 Who currently maintains and understands the codebase?
A single individual within the Department of Finance — Anas Odeh (System Administrator) currently maintains and understands the codebase.
1.6 Has the code been reviewed by anyone other than its author(s)?
No — the code has been AI-assisted and self-reviewed by its author (Anas Odeh) only; it has not undergone independent third-party review.
1.7 Current release and change process (who authorizes, who deploys)?
Source is maintained under Git version control. Changes are built and published from Visual Studio using a Web Deploy / FTP publish profile to the hosting environment; Razor views are compiled into the application, so any change requires a rebuild and redeploy, while static assets under wwwroot/ are shipped as part of the same publish. To avoid locked-file errors an app_offline.htm is placed during deployment. The process is documented in docs/DEPLOY.md. Changes are currently authorized and deployed by Anas Odeh (System Administrator).

3. Scope, Usage and Timeline

3.1 Purpose of the application (2–3 sentences)
GovBudget is a web-based Performance-Based Budgeting system used by the Department of Finance and government entities to prepare, submit, review and consolidate annual budgets. It captures programme/activity structures, KPIs, mid-year forecasts and current-year actuals, runs step-down cost allocation from support to mandate programmes, and produces management-review and Power BI reporting.
3.2 Expected number of users at go-live, and number of departments/entities
The system is intended to serve all entities under the Department of Finance's horizon. The current PBB scope covers approximately 6 entities, 22 programmes and 67 activities, and will expand as further entities are onboarded.
3.3 Is use mandatory or optional?
Mandatory — use will be mandatory following approval and implementation.
3.4 Is the application already in use?
Yes — the system is running in a pilot phase on external hosting. The purpose of this request is to redirect the hosting onto the local government server (the FINBUDGET server) under EGA infrastructure.
3.5 Requested go-live date and any fixed deadline/business cycle driving it
1 September 2026, aligned to the FY budget-preparation cycle.
3.6 Does it integrate with, replace, or run parallel to any existing government system?
It replaces the existing Excel-spreadsheet-based budget-preparation process. It does not integrate with or run parallel to any other government system; source data is brought in via Excel/file import, and it exposes SQL views consumed by Power BI for reporting.
3.7 Were any paid AI tools, subscriptions or third-party APIs used to build or operate it?
Yes, for development only — a Windsurf AI coding-assistant subscription was used during development. At runtime the application does not depend on any paid AI service or third-party API.

4. Architecture, Data and Testing

4.1 Technology stack (language/framework, database, hosting)
  • Framework/Language: ASP.NET Core MVC on .NET 10 (net10.0), C#; server-rendered Razor views.
  • Data access: Entity Framework Core 10.0.2 (SQL Server provider).
  • Database: Microsoft SQL Server (single relational database, core schema).
  • Reporting/Export: ClosedXML for Excel export; Power BI reads dedicated SQL views.
  • Front-end: Bootstrap 5, Bootstrap Icons, jQuery.
  • Hosting model: Windows Server + IIS with the .NET 10 ASP.NET Core Hosting Bundle; HTTPS enforced.
Full detail is in the accompanying GovBudget_EGA_Technical_Requirements.html.
4.2 Expected data volume, annual growth, peak concurrency, seasonal peaks
Data volume is modest — budget lines, KPIs, HR cost allocations and imported monthly actuals per entity per year. The primary seasonal peak is the annual budget-preparation window and the mid-year review, when concurrency is highest.
4.3 What automated test coverage exists?
None — there is currently no automated test project. Validation to date has been manual functional testing.
4.4 Has load/performance testing been done?
No. Given the small, internal user base, load has not been formally tested.
4.5 If multi-entity, how is data separation enforced and verified?
The application is single-database, multi-entity. Access is controlled by cookie authentication with role- and entity-scoping: each non-administrator user carries an EntityId claim and all data queries are filtered to that entity; global administrators (SYSADMIN, or ADMIN without an entity claim) may see all entities. Separation is enforced in the application layer on every scoped query.
4.6 External services depended on at runtime (CDNs, third-party APIs, hosted libraries)
  • Microsoft SQL Server database (primary dependency).
  • Bootstrap Icons stylesheet currently served from the jsDelivr CDN (to be localised for a fully self-contained government deployment).
  • No third-party runtime APIs; jQuery and Bootstrap are served locally from the application.
  • (Future/optional) an SMTP relay for password-reset notifications.
4.7 Does the application maintain an audit trail of user actions and data changes?
Yes, partial. The system writes to an AuditLogs table (e.g. logins, password-reset requests, key inserts/updates) and most transactional tables carry CreatedBy/CreatedAt and UpdatedBy/UpdatedAt fields; budget submissions retain an approval/return audit history. Coverage is not yet exhaustive across every action.

5. Security, Data Protection and Compliance

5.1 How is the information classified?
Confidential — government budget and financial planning data.
5.2 Does it hold personal data relating to identifiable individuals?
Yes. Categories held: application user identities (usernames and, for password-reset requests, optional contact information); and HR-related cost data (employee cost records and occupation/allocation information used for manpower budgeting).
5.3 How do users currently authenticate?
Local accounts with passwords held by the application (cookie-based sign-in).
DisclosurePasswords are currently stored and compared in plain text (a development/demo shortcut, clearly marked in the code for replacement). This must be remediated with a proper password hash (e.g. ASP.NET Core Identity / PBKDF2 or BCrypt) before production go-live, or superseded by SSO (see 5.4).
5.4 If not integrated, is the department open to Active Directory / Entra SSO?
Yes. The cookie-authentication design can be replaced with AD/Entra single sign-on; DoF is open to adopting government SSO as directed by EGA.
5.5 Is multi-factor authentication in place or planned?
No MFA within the application itself — MFA would most naturally be provided via AD/Entra/UAE PASS SSO if adopted.
5.6 How are administrative privileges granted, recorded and reviewed?
The application uses role-based authorization with ADMIN and SYSADMIN roles (an AdminOnly policy protects administrative areas). Roles are assigned through the in-app administration area by a system administrator and stored on the user record; administrative actions are captured in the audit log. Administrator accounts are reviewed by the system administrator (Anas Odeh) as part of periodic account review.
5.7 Has any security assessment been performed?
No assessment performed. DoF is willing to support an EGA-led security assessment as part of onboarding.
5.8 Have third-party/open-source licensing terms been reviewed as suitable for government use?
Yes. All principal components are permissively licensed (MIT): .NET / ASP.NET Core, Entity Framework Core, ClosedXML, Bootstrap, Bootstrap Icons and jQuery. No copyleft or commercially-restricted components are used at runtime.
5.9 Known weaknesses, unresolved defects or temporary configurations to address before go-live
Disclosed proactively:
  • Plain-text passwords — to be replaced with hashing or SSO before production.
  • Secrets in configuration — the database connection string currently sits in appsettings.json; to be moved to environment variables / a secrets vault, and credentials rotated, on migration to EGA hosting.
  • No MFA — pending SSO adoption.
  • No automated test suite — validation is manual to date.
  • AllowedHosts = * — to be tightened to the assigned government domain in production.
  • External CDN — Bootstrap Icons load from jsDelivr; to be localised for a self-contained deployment.
None of these are functional defects; they are hardening items appropriate to move from a departmental build to government infrastructure, and DoF is committed to remediating them as onboarding conditions.

6. Hosting, Backup and Recovery

6.1 Hosting environment preference
No strong preference — DoF defers to EGA (EGA government data centre or an approved environment).
6.2 Which environments are required?
Production, User Acceptance Testing (UAT) and a Development environment.
6.3 Required Recovery Point Objective (max acceptable data loss)
Up to 24 hours (daily backup), with tighter recovery achievable via transaction-log backups if provided by EGA.
6.4 Required Recovery Time Objective (max acceptable downtime)
Same business day; the system is not real-time-critical outside the budget-preparation and review windows.
6.5 Required backup retention period and its basis
Retention per RAK Government records-management and financial-records policy; DoF will align to the retention standard applied by EGA on the hosting platform.
6.6 Monitoring, alerting and log retention expectations, and who receives alerts
The application logs via standard ASP.NET Core logging (Information level; framework at Warning) and can route to files, the Windows Event Log or a central sink as EGA prefers. Availability and error alerts should be directed to the system administrator (Anas Odeh) and to the EGA operations team.
