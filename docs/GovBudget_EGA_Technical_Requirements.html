2. System overview

GovBudget is a web-based Performance-Based Budgeting (PBB) system used by the Department of Finance and government entities to prepare, submit, review and consolidate annual budgets, capture actuals, run cost allocation, and produce management-review and Power BI reporting.

It is a server-rendered ASP.NET Core MVC application backed by a single Microsoft SQL Server database. All users access it through a standard web browser; there is no desktop client.

4. Server / hosting requirements

  • OS: Windows Server (IIS) — current deployment model. Linux + Kestrel is technically possible but not the validated target.
  • Web server: IIS with the .NET 10 ASP.NET Core Hosting Bundle (installs the ASP.NET Core Module / ANCM for in-process hosting).
  • Application pool: "No Managed Code" (ASP.NET Core runs its own runtime), 64-bit.
  • HTTPS: required — the app enforces HTTPS redirection and HSTS in production.
  • Outbound access: to the SQL Server host, and (unless Bootstrap Icons are localised) to the jsdelivr CDN.
  • File system: write access to the app folder for deployment and to place/remove app_offline.htm; standard temp space for report generation.
  • Session state: in-memory (single instance). A load-balanced multi-instance deployment would need sticky sessions or a shared session store.

5. Database requirements

  • Engine: Microsoft SQL Server (Azure SQL / SQL Server 2019+ compatible).
  • Connection: configured in appsettings.json under ConnectionStrings:DefaultConnection. Connections use Encrypt=True.
  • Resilience: the app enables EF Core retry-on-failure (3 retries) and a 120-second command timeout for heavier report/consolidation queries.
  • Schema: provisioned from the SQL scripts in /docs and root (e.g. LocalDatabase_FullSchema.sql, PBB_PerformanceSchema.sql, ReportingRedesign_Schema.sql, SetupMissingTables.sql).
  • Startup guards: on start the app seeds core budget categories (REVENUE / OPEX / CAPEX); additional idempotent schema checks run in the Development environment only.
  • Login: a dedicated SQL login with db_owner (or equivalent DDL + DML) on the application database.
Credentials Database server address and credentials are provided separately through a secure channel and are not included in this document. Production secrets should be stored using environment variables / user-secrets / a secrets vault rather than in appsettings.json.

6. Networking, DNS & TLS

  • Public URL / domain: to be assigned by EGA (e.g. a *.rak.ae host); DNS A/CNAME record required.
  • TLS certificate: valid certificate for the assigned domain (bound in IIS). HSTS is enabled in production.
  • Ports: 443 (HTTPS) inbound; 80 redirect to 443. Outbound to SQL Server port (typically 1433) and HTTPS (443) for the icon CDN.
  • Allowed hosts: currently * in configuration; should be tightened to the assigned domain(s) in production.

7. Security & authentication

  • Authentication: cookie-based (ASP.NET Core cookie authentication). Login at /Account/Login.
  • Authorisation: role-based. Roles include ADMIN and SYSADMIN; an AdminOnly policy protects administrative areas. Non-admin users are scoped to their entity.
  • Password reset: currently a manual/administrator-mediated flow (no email sender wired). An SMTP notifier can be enabled later without code changes to callers — SMTP relay details would be required from EGA.
  • Transport security: HTTPS enforced; encrypted database connections.
  • Data classification: the system holds government financial/budget data — access is restricted and should be hosted within the approved government environment.

9. Deployment & release process

Razor views are compiled into the application assemblies, so any view or code change requires a rebuild and redeploy; static assets under wwwroot/ are served as-is. A full Publish covers both. Recommended: Visual Studio Web Deploy (incremental) or an FTP publish profile. To avoid locked-DLL errors during redeploy, drop an app_offline.htm in the site root before the copy and remove it afterwards (Web Deploy does this automatically). Full details are in docs/DEPLOY.md.

Cache Static assets are versioned (asp-append-version), so browsers automatically pick up updated CSS/JS after a deploy.

10. Backup, recovery & retention

  • Database backups: automated daily full backups plus transaction-log backups; retention per government policy (to be confirmed with EGA).
  • Recovery: point-in-time restore capability required; documented RPO/RTO targets to be agreed.
  • Application: stateless aside from session; recovery = redeploy from source + restore database. Source is under version control (Git).

11. Monitoring, logging & support

  • Logging: ASP.NET Core logging (default Information; framework at Warning). Can be routed to files / Windows Event Log / a central log sink as EGA prefers.
  • Health: the home page and a database connectivity check serve as basic availability signals.
  • Support model: maintained by the Department of Finance application team; EGA to provide infrastructure/platform support.

12. Client (end-user) requirements

  • Modern desktop browser: latest Microsoft Edge, Google Chrome, or Firefox.
  • No plug-ins or client installation; HTTPS access to the site URL.
  • Excel (or compatible) to open exported .xlsx reports; Power BI Desktop/Service for reporting consumers.

13. Environments & sizing

EnvironmentPurposeNotes
ProductionLive use by DoF and entitiesDedicated app + database.
Staging / UATTesting & sign-off before releaseRecommended; mirrors production configuration.

Indicative sizing (to be right-sized with EGA): a single web instance with 2 vCPU / 4–8 GB RAM handles the expected concurrent user base of government entities; the database is the primary scaling factor for reporting/consolidation. Load can be scaled vertically first; horizontal scale-out requires a shared session store.

14. Data migration & integrations

  • Data load: master data and historical actuals are imported via the application (Excel import) and the provided SQL scripts.
  • Reporting integration: Power BI connects to dedicated SQL views (documented in docs/PowerBI_Reporting_Guide.md and the PowerBI_*_View(s).sql scripts).
  • Future: optional SMTP integration for password-reset / notifications.
